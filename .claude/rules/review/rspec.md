# レビュー観点：RSpec

このプロジェクトでコードを書くとき・レビューするときに確認する観点。

## 書き方

- [ ] `describe` はテスト対象（クラス・メソッド・機能）、`context` は条件、`it` は期待する結果を表している
- [ ] 説明は具体的に書く。「正しいこと」「正常に動くこと」のような、何を確かめているか分からない書き方をしていない
  - NG：「料金が正しく計算されること」 OK：「割引後の単価が 0 円未満のときは小計が 0 円になること」
- [ ] 期待値の根拠が同じテストの中で分かる。別の場所（factory の既定値など）を見ないと期待値の理由が分からない書き方をしていない
- [ ] 入力値と期待値はベタ書きにする。計算式や定数から期待値を導いていない
- [ ] 準備・実行・検証（AAA）を分けて書く。実行を `before` に書いていない
- [ ] 検証に使う値は、読んだだけで意味が分かる値にする（例：個数の合計を確かめるなら 1 と 2 ではなく、合計が一意に決まる 3 と 5 など）
- [ ] 検証に関係しない値をテストに書いていない。あえて書くときは理由をコメントに残す
- [ ] `let` / `let!` を多用していない。遅延評価が要らないなら `before` かローカル変数を使う

## system spec

- [ ] 操作した後の画面の変化（表示されたメッセージ・一覧の内容）まで確認している
- [ ] 要素は CSS クラスではなく `data-test-id` などのテスト専用の属性で指定する
- [ ] 「表示されないこと」だけを確かめていない。同じテストか対になるテストで「表示される条件」も確かめる（文言の誤りなどで常に通ってしまうのを防ぐ）
- [ ] `sleep` で待たず、表示される要素で待つ

## model spec

- [ ] Rails やライブラリの標準機能（単純な presence・length など）のテストを書いていない
- [ ] すべての組み合わせを網羅しようとせず、境界値と業務ルールに絞る
  - このプロジェクトでは 9:59 / 10:00 / 10:01、14 日先 / 15 日先、残数ちょうど / 1 不足、1 日 3 個 / 4 個 などの境界を優先する
- [ ] 数値の範囲は、下限ちょうど・下限 - 1・上限ちょうど・上限 + 1 の境界値を model spec で確認している

## FactoryBot

- [ ] factory にはバリデーションを通すのに必要な属性だけを書く
- [ ] モデル（DB）に既定値がある属性を factory に書いていない（例：`on_sale { true }`・`active { true }`・`status { 'ordered' }`）。テストに必要な値はテスト側で明示する
- [ ] よく使う組み合わせ（キャンセル済みの注文、非販売の弁当など）は `trait` にまとめる

## その他

- [ ] `action_on_unpermitted_parameters` を `:raise` にして、Strong Parameter の許可漏れを検知する
