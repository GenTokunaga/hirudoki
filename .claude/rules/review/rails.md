# レビュー観点：Rails（Model / View / Controller）

このプロジェクトでコードを書くとき・レビューするときに確認する観点。

## Model

- [ ] `default_scope` を使っていない。並び順や絞り込みは名前の付いた `scope` で明示する
- [ ] 属性の既定値は DB の default か `attribute :xxx, default:` で定義し、gem の default オプションに頼らない
- [ ] マイグレーションの中でモデルクラスを参照していない。データの更新が必要なら SQL かメンテナンススクリプトで行う
- [ ] 一覧や集計は DB 側で処理している（`pluck`・`group`・`count`）
- [ ] `has_many` は `preload` で読み込む
- [ ] NOT NULL・CHECK・一意インデックス・外部キーを DB にも付けている
- [ ] コールバックで通知や別レコードの作成などの副作用を起こしていない。必要なら名前の付いたメソッドにしてコントローラーから呼ぶ
- [ ] `scope` は必ず `ActiveRecord::Relation` を返す（`first` や `nil` を返す処理は scope ではなくクラスメソッドにする）
- [ ] モデルの中で `Time.current` / `Date.current` を直接使っていない。締切判定など時刻に依存する処理は、日時を引数で受け取れるようにする
  - このプロジェクトでは「当日 10:00 締切」「当日〜14 日先」の判定が該当する。テストで `travel_to` を使わずに済む形にする
- [ ] 参照されているレコードの削除は `dependent: :restrict_with_error` で止める。`dependent: :destroy` が本当に必要か確認する
- [ ] 発行される SQL を確認し、N+1 や不要なクエリがない
- [ ] 複数の条件を並べるときは、軽い条件（メモリ上の比較）を先、重い条件（クエリ）を後に書く
- [ ] テーブルにない業務上の概念（料金計算、定期注文の生成など）は、モデルに詰め込まず PORO のクラスに切り出す
- [ ] preload した関連に対して `where` などで再度クエリを発行していない。条件付きで使うなら scope 付きの関連を定義して preload する
- [ ] ジョブにはロジックを書かず、モデルのメソッドを呼ぶだけにする
- [ ] 複数レコードの更新はトランザクションで囲む
- [ ] 大量データのループは `find_each` を使う
- [ ] 外部 API の呼び出しは失敗する前提で、リトライやエラー処理を考えている
- [ ] バリデーションは最初から厳しめに書く（文字数の上限、数値の範囲、整数かどうか、形式）。後から厳しくすると既存データが通らなくなる

## View

- [ ] ビューに条件分岐や計算などのロジックを書いていない。ヘルパー・モデル・デコレーターへ移す
- [ ] 画面の種類ごとにレイアウトが大きく違うなら、レイアウトファイルを分ける
- [ ] パーシャル・コンポーネントのルート要素は 1 つ。ルート要素にマージンを持たせず、余白は親側で付ける
- [ ] 使えない操作はボタンを消さずに非活性（`disabled`）にし、使えない理由も表示する
  - このプロジェクトでは、締切後の注文の「変更」「キャンセル」が該当する
- [ ] I18n のキーは `t('.xxx')` の相対指定ではなく絶対キーで書く
- [ ] CSS クラス名を文字列連結で組み立てていない（`"text-#{color}"` など）。全文を書くと検索でき、未使用クラスの削除で消されない
- [ ] 「詳細」「こちら」のような汎用の文言をリンクにしていない。対象の名前自体をリンクにする
- [ ] 見た目の調整のために `h1`〜`h6`・`br`・`strong` などを使っていない。見た目は CSS クラスで調整する
- [ ] Stimulus コントローラーは自分の要素の配下だけを操作する
- [ ] GET 以外のリクエスト（削除・状態変更など）は `link_to` ではなく `button_to` を使う
- [ ] 日時は `I18n.l` で表示する
- [ ] Turbo Frame / Stream に使う ID には `turbo_` のプレフィックスを付ける

## Controller

- [ ] ルーティングは `resources` / `resource` で定義する
- [ ] コントローラーはリクエストの受け取りとレスポンスの準備だけにし、業務ロジックはモデルへ移す
- [ ] 名前空間ごとに基底コントローラー（`Admins::ApplicationController` など）を継承する
- [ ] セッションには ID などの最小限の値だけを保存する
- [ ] `current_user` を直接 `update` しない。更新するときは `User.find(current_user.id)` で別のインスタンスを取得する（更新に失敗しても画面上のログインユーザーの値が書き換わらないように）
- [ ] 一覧の取得には必ず `order` を付ける。同じ値が並ぶ列で並べるときは `id` も足して順番を固定する
- [ ] ルーティングをネストしたら `module:` も指定する
- [ ] 7 つの基本アクションに収まらない操作は、URL をモデルに合わせず、操作そのものを独立したリソースとして切り出す（例：定期注文の生成 → `resource :generation`）
- [ ] レコードはログインユーザーを起点に取得する（`current_user.orders.find(params[:id])`）
- [ ] メール送信などの副作用は保存処理と分ける
- [ ] 管理者と利用者で namespace を分ける
- [ ] 削除の結果を確認しないなら `destroy!` を使う
  - 例外：`restrict_with_error` で削除できないことが業務上あり得る場合は、`destroy` の戻り値で分岐し、理由を画面に表示する（想定できる失敗は例外にしない）
