# レビュー観点：一般

このプロジェクトでコードを書くとき・レビューするときに確認する観点。
Rails 固有の観点は `review/rails.md`、テストは `review/rspec.md`、金額計算は `review/money.md` にある。

## 書き方

- [ ] seed やスクリプトでのデータ登録は `create!` などの `!` 付きメソッドを使い、失敗に気づけるようにする
- [ ] `&.` や `presence` を「念のため」付けていない。nil になり得る箇所だけに付ける
- [ ] 想定できる失敗（入力の誤り、在庫不足、締切後の操作など）を例外と `rescue` で処理していない。事前にチェックして分岐する。例外はネットワーク障害など、事前に防げないものだけに使う
  - 例：パラメーターの日付の解釈は、`rescue Date::Error` ではなく、形式を確認してから変換する
- [ ] `send` / `public_send` で呼び出すメソッドを動的に決めていない。呼び出し元で分岐を書く
- [ ] 自前のループや一時変数で書いている処理を、`Enumerable` のメソッド（`sum`・`group_by`・`partition`・`each_with_object` など）で書けないか
- [ ] 条件分岐は肯定形で書く（`unless` + 否定形、二重否定を避ける）
- [ ] 自前で実装する前に、Rails や gem に同じ機能がないか調べた
- [ ] 外から呼ばれないメソッドは `private` にする

## 設計

- [ ] 今必要のない機能・引数・設定を先回りして作っていない（YAGNI）
- [ ] 名前から中身が推測できる。`data`・`info`・`check_xxx` のような曖昧な名前や、結果が分からない名前を避ける
- [ ] 1 つのメソッド・クラスに 1 つの役割だけを持たせている
- [ ] 禁止リスト（`except`・`reject`）より許可リスト（`only`・`select`）を使う

## ファイル・依存関係

- [ ] 中身が空のファイル（生成されたままのヘルパー・スタイルシートなど）を残していない
- [ ] gem のバージョンを理由なく固定していない。固定するときは理由をコメントに残す
- [ ] 開発環境と本番（Heroku）で構成の違い（DB、タイムゾーン、画像の保存先、環境変数）による不具合が起きないか

## コメント

- [ ] コメントにはコードで表せなかった理由（言い訳）だけを書き、処理の説明は書いていない

## レビューの進め方

- [ ] 指摘が「好み」なのか「良し悪し」なのかを区別する。良し悪しの指摘には「なぜそのほうがよいのか」を添える
