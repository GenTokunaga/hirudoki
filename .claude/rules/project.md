# プロジェクト固有ルール（hirudoki）

「ひるどき」は、日替わりの弁当を注文すると自宅やオフィスまで届けてくれる宅配サイトです。 利用者はその日の献立を見て注文し、管理者は献立・注文・配達を管理します。

## ビュー

- ビューファイルは ERB ではなく Haml で書く（`*.html.haml`）
  - 例外：HTML 以外のテンプレート（メールのテキスト版 `*.text.erb`、`*.json.erb` など）は ERB のままでよい
  - 書いたら `bundle exec haml-lint` で指摘がないことを確認する

## コメント

- コメントには言い訳を書く（コードで表現できなかった理由だけを残す）
  - 例：「×× の方がすっきりするが、性能のためにあえてこう書いている」「本当は ×× したかったが、〇〇 の理由で諦めた」
  - 理由を残すときは `NOTE:` を付ける。後でやることは `TODO:`、直すべき問題は `FIXME:`
- コードの動作を説明するコメントは書かない（コードと内容が重複し、修正漏れで食い違う）
  - 説明が必要に感じたら、まずメソッド名・変数名・メソッドの分割で表現できないか考える
- spec で検証に使わない値をあえて指定するときは、その理由をコメントで残す
- gem のバージョンを固定するときは、固定する理由をコメントで残す（関連する issue があればリンクも）
- 参考：『コードレビューの教科書』5.16「コメントには言い訳を書く」

## ルーティング

- パスは `resources` / `resource` で定義する。`get` / `post` / `patch` などで URL とアクションを個別に結び付けない
  - 例外：トップページの `root`、Devise の `devise_for`
  - 標準の 7 アクションに収まらない操作は、サブリソースとして切り出してネストする（例：`resources :orders do resource :payment, only: :create end`）
  - 使うアクションは `only:` で明示する（不要なルートを作らない）
- ユーザーから見て 1 つしかないもの（ダッシュボード、マイページなど）は単数の `resource` を使い、URL に id を含めない
- ルーティングをネストしたら `module:` も指定し、コントローラーの配置と対応させる
- 管理者と利用者は namespace を分ける。管理画面は `namespace :admins`（URL は `/admins`）とし、`path:` で別の URL を付けない
- 参考：『コードレビューの教科書』3.1・3.7・3.11・3.14
